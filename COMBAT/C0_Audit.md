# C0 audit/design lock — C1 implementation scope

Baseline: 3f4dabe (SO2 layout and tested P4). The user requested C01: audit plus C1 foundation. C2–C5 are not included.

- PlayerInput emits a mouse request; EquippedTool rotates the existing axe, checks ToolHitQuery once at ContactProgress and completes its swing. ToolHitQuery uses the existing group/arc/closest-point interface; trees wobble/drop leaves and Entity takes one damage. Retain this compatibility path, including tree/fire semantics.
- Entity owns HP, red flash and death fade today. GroundChase is its sole mover; PlayerMovement is the player's sole mover. Both use existing feet collision/default masks; this pass adds no hitboxes, hurtbox physics, layers, movement impulses or collision changes.
- SO2 persistent roots and WorldScene's typed references stay unchanged. No scene or existing resource files need editing. P4 reads Entity.Health and restores living test skeleton health; preserve that API as a view of the shared component, not a second HP counter.
- Shared health lives in ENTITIES/Shared/Health as a plain C# state object. One ActorStats cache per actor holds all four values, with instance-local modifier IDs and optional shared Resource base values. COMBAT/Damage owns immutable request/result values, deterministic resolution and the shared receiving contract. No frame callbacks, Node per stat, registry or world-path dependency.
- Formula: effective stat = clamp((base + sum(flat)) * max(0, 1 + sum(additive percentages)) * product(multipliers)). Modifier IDs are unique per actor, ordinal-sorted for reproducible floating-point order; replacing/removing invalidates only that actor. Profiles emit Changed; cache reads rebuild once after a real change. Percent units: 0.25 = +25%. Damage is a multiplier, defense is flat reduction, attack/move speed are multipliers over authored timing/speed.
- Damage: base attack damage * attacker damage multiplier, minus defender flat defense, clamp >=0, round once away from zero, cap 1,000,000, then apply at most remaining HP. No implicit one-damage minimum. Zero/blocked damage causes no HP event or flash. Living/dead state derives from the single health source; repeated lethal hits cannot emit duplicate death.
- First tuning values: max health, damage multiplier, flat defense, attack-speed multiplier and movement-speed multiplier. MaxHealth/WalkSpeed/MoveSpeed remain in their existing definitions; optional CombatStatProfile supplies neutral default multipliers/defense without editing canonical resources.
- Player receives damage through the same contract but is not added to the axe's tool-target group. Death disables movement/input/tool presentation, retains the player for save/location ownership, and never deletes a run. No enemy attack or death/retry screen is introduced yet.
- Save schema 2 adds optional player HP to the record type. New schema-2 checkpoints require valid HP; schema-1 checkpoints may omit it and explicitly restore full configured HP. Unknown versions still fail. Macro/feature/chunk schemas, content fingerprint and IDs remain unchanged. Conversion is non-destructive; save writes preserve the previous checkpoint backup. Runtime modifier persistence waits for actual equipment/buff ownership.
- C2 recommendation: shared actor-damage receiving interface plus existing IToolHitTarget adapter, short contact-window spatial/physics queries rather than idle Area2Ds. Player and AI will submit the same request with different intent adapters; faction/hurtbox decisions belong to C2. Keep current hit geometry until that phase, so C1 is independently testable.
- Implement C2 enemy attacks before broad movement polish; tune one fair encounter and then C3 feedback/C4 movement. Do not invent a shared motor or EffectsRoot until actual impulse/standalone-FX needs justify it.

Validation: deterministic stats/order/clamps/rounding, HP/healing/death/restore, idle cache reuse, player/entity receiving, baseline tool hits, P4 new HP plus actual old schema-1 disk files, SO2/streaming and tree/fire/light regressions. Visual feel/performance requires target-machine playtesting. Rollback uses an isolated baseline checkout and preserved backup; do not reset user saves or hand-edit checksums.
